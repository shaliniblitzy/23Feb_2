# =============================================================================
# Payment Service — Python Dependencies
# =============================================================================
# Target runtime  : Python 3.11+
# Service domain  : Dual-provider (Stripe + Razorpay) payment processing
#                   service. Implements the PaymentProvider adapter layer,
#                   webhook signature verification, idempotency-key store,
#                   envelope-encryption helpers (encryption at rest), and the
#                   Kafka producer for payment.succeeded / payment.failed /
#                   payment.refunded events.
# Source of truth : Agent Action Plan (AAP) Section 0.3.1 (public packages),
#                   Section 0.3.3 (dependency updates), Section 0.4.2
#                   (Stripe + Razorpay external integrations + retries +
#                   provider failover), Section 0.4.4 (payment_db PostgreSQL
#                   schema with the five tables: payments,
#                   payment_attempts, refunds, provider_webhooks,
#                   idempotency_keys), and applicable rules R-8 (encryption
#                   at rest + idempotency key store), R-10 (dual-provider
#                   concurrent integration behind PaymentProvider), R-12
#                   (HMAC webhook signature verification + idempotent
#                   webhook processing), R-14 (Schema Registry), R-15
#                   (retry with exponential backoff + jitter), R-16
#                   (circuit breaker), R-17 (DLQ / retry topics), R-21 /
#                   R-22 (JWT validation with bounded TTL JWKS cache),
#                   R-26 / R-27 (structured JSON logs shipped via Beats to
#                   Logstash), R-30 (event naming conventions).
#
# Pinning policy  : Every package carries a lower bound (>=) and an upper
#                   bound (<) excluding the next major version. This permits
#                   safe patch / minor upgrades while preventing breaking
#                   major-version drift. No package is left bare; no `==`
#                   pinning is used unless accompanied by a "# pin: <reason>"
#                   comment.
#
# Ordering        : Grouped by concern, alphabetized within each group for
#                   deterministic diffs. Runtime dependencies appear first;
#                   testing (dev) dependencies are gathered at the bottom
#                   under the "Testing (dev)" banner.
#
# Install         : python -m pip install -r requirements.txt
# Compile wheels  : pip wheel -r requirements.txt -w /tmp/wheels
# Audit CVEs      : pip-audit -r requirements.txt
# =============================================================================

# and monitoring dashboards (AAP Section 0.3.1 — confluent-kafka).
# -----------------------------------------------------------------------------

# -----------------------------------------------------------------------------
# Database — PostgreSQL (payment_db, encrypted at rest — AAP R-8)
# -----------------------------------------------------------------------------
# The Payment Service owns its own data store per AAP Rule R-6 (database-
# per-service). The store is PostgreSQL with five tables — `payments`,
# `payment_attempts`, `refunds`, `provider_webhooks`, `idempotency_keys`
# — per AAP Section 0.4.4. Encryption at rest (AAP R-8) is realized via
# column-level envelope encryption using KMS-issued data keys (see the
# KMS Clients group below) on top of cluster-level disk encryption.
# psycopg v3 (NOT psycopg2) provides native asyncio support and a
# built-in connection pool; SQLAlchemy 2.0 layers async ORM / query-
# builder semantics on top with the postgresql+psycopg:// dialect URL.
# alembic runs migrations under `migrations/` on container startup or via
# a dedicated migration job (AAP R-9).
# -----------------------------------------------------------------------------
alembic>=1.13.0,<2.0.0                                     # AAP R-9 — migration runner for the five payment tables
psycopg[binary,pool]>=3.1.18,<4.0.0                        # PostgreSQL driver v3 (binary wheel + connection pool)
sqlalchemy>=2.0.25,<3.0.0                                  # AAP Section 0.4.4 — async ORM / query builder over psycopg v3


# -----------------------------------------------------------------------------
# HTTP Client — Outbound to Provider APIs
# -----------------------------------------------------------------------------
# httpx is the async-first HTTP client used directly for Razorpay REST
# calls (the official Razorpay SDK is sync-only) and as the underlying
# transport for any custom Stripe REST calls outside the official SDK.
# It supports per-request timeouts, transport-level retries (combined
# with `tenacity` below), HTTP/2, and cleanly integrates with respx for
# tests. Outbound calls to Stripe, Razorpay, and any signed-webhook
# verification endpoints are wrapped by the resilience decorators per
# AAP R-15 / R-16.
# -----------------------------------------------------------------------------
httpx>=0.27.0,<1.0.0                                       # AAP Section 0.4.2 — async HTTP client w/ HTTP/2 + timeouts


# -----------------------------------------------------------------------------
# Payment Provider SDKs (AAP R-10 — dual-provider concurrent integration)
# -----------------------------------------------------------------------------
# Per AAP R-10 the Payment Service MUST integrate Stripe AND Razorpay
# concurrently behind a unified `PaymentProvider` interface; provider
# selection is data-driven at runtime via currency, region, or merchant
# preference (env vars STRIPE_ENABLED / RAZORPAY_ENABLED gate provider
# initialization without rebuilding the image). BOTH SDKs ship in every
# image so operators can flip providers or enable Stripe→Razorpay
# fallback (and vice versa) instantly. This is non-negotiable: dropping
# either SDK violates AAP R-10.
#
# Stripe SDK upper bound `<13.0.0` is intentionally wide because the
# Stripe SDK has had several major-version releases in a short window
# (v8 → v9 → v10 → v11 → v12); the API version pin is enforced at
# runtime via the STRIPE_API_VERSION env var, NOT via an SDK pin.
# Razorpay's official Python SDK is published under the `razorpay`
# distribution name (1.4.x line); the SDK is sync-only and is wrapped
# with `run_in_executor` for async use OR replaced by direct httpx REST
# calls in src/providers/razorpay/.
# -----------------------------------------------------------------------------
razorpay>=1.4.2,<2.0.0                                     # AAP R-10 — RazorpayProvider adapter (India-focused; sync SDK)
stripe>=9.0.0,<13.0.0                                      # AAP R-10 — StripeProvider adapter (global; multi-major upper bound documented)


# -----------------------------------------------------------------------------
# Resilience — Retry, Backoff, Circuit Breaker
# -----------------------------------------------------------------------------
# tenacity provides retry decorators with exponential backoff + jitter,
# bounded attempts, and configurable predicates per AAP R-15. Retries
# protect every Stripe / Razorpay HTTP call and every Kafka produce
# attempt. pybreaker wraps each outbound provider call site with a
# thread-safe in-process circuit breaker (open / half-open / closed) per
# AAP R-16; on Stripe circuit-open the routing strategy can fall back to
# Razorpay (and vice versa) when both providers are eligible for the
# given currency/region. Both libraries are explicitly listed as
# canonical examples in AAP Section 0.3.1 alongside resilience4j and
# opossum, and they match the resilience stack used by sibling services
# (notification-service, recommendation-engine) for operational
# consistency.
# -----------------------------------------------------------------------------
pybreaker>=1.2.0,<2.0.0                                    # AAP R-16 — circuit breaker (open / half-open / closed states)
tenacity>=8.2.3,<9.0.0                                     # AAP R-15 — retry w/ exponential backoff + jitter, bounded attempts


# -----------------------------------------------------------------------------
# Authentication — JWT Validation Only
# -----------------------------------------------------------------------------
# Per AAP R-21, the Auth Service is the SOLE issuer of JWT tokens; this
# service VALIDATES ONLY, never signs. pyjwt[crypto] supports RS256/ES256
# verification using public keys fetched from the Auth Service JWKS
# endpoint. cachetools provides the bounded-TTL JWKS key cache mandated
# by AAP R-22 — keys are refreshed automatically without restart, which
# enables seamless key rotation in the Auth Service.
# -----------------------------------------------------------------------------
cachetools>=5.3.0,<6.0.0                                   # AAP R-22 — bounded TTL cache for JWKS keys
pyjwt[crypto]>=2.8.0,<3.0.0                                # AAP R-21 / R-22 — JWT validation only (RS256/ES256)


# -----------------------------------------------------------------------------
# Cryptography — Webhook Signature Verification + Envelope Encryption
# -----------------------------------------------------------------------------
# `cryptography` is transitively installed by `pyjwt[crypto]`; pinning it
# explicitly here makes CVE-driven version bumps auditable in this single
# manifest rather than buried in transitive resolution. The Payment
# Service uses `cryptography` directly for two distinct concerns:
#
#   1. HMAC-SHA256 webhook signature verification (AAP R-12). Stripe
#      sends a `Stripe-Signature` header; Razorpay sends a
#      `X-Razorpay-Signature` header. Verification MUST run on the raw
#      request body BEFORE any JSON parsing to prevent canonicalization
#      drift. Python's stdlib `hmac` + `hashlib` cover the SHA-256
#      primitive; `cryptography` is retained for asymmetric primitives
#      (RSA / EC) used by some webhook providers and for Fernet symmetric
#      keys.
#
#   2. Envelope-encryption helpers for column-level encryption (AAP R-8).
#      Sensitive columns (PII, last4 not derivable, idempotency
#      payloads) are encrypted with Fernet using a per-row data encryption
#      key (DEK) wrapped by a KMS-issued key encryption key (KEK). See
#      src/security/envelope.py for the canonical wiring.
# -----------------------------------------------------------------------------
cryptography>=42.0.0,<43.0.0                               # AAP R-12 (HMAC webhook signature verification) + R-8 (envelope encryption)


# -----------------------------------------------------------------------------
# KMS Clients — Encryption-at-Rest Key Management (AAP R-8)
# -----------------------------------------------------------------------------
# AAP R-8 mandates that the Payment Service database is encrypted at
# rest. Encryption is realized via envelope encryption (see the
# Cryptography group above): per-row data encryption keys (DEKs) are
# generated and wrapped by a KMS-issued key encryption key (KEK). The
# KMS backend is selected at runtime via the ENCRYPTION_PROVIDER env
# var; we ship clients for AWS KMS (boto3) and HashiCorp Vault Transit
# (hvac) out-of-the-box. Other KMS providers (GCP KMS, Azure Key Vault)
# are pluggable via a deployment-specific requirements-extra.txt.
#
# botocore is pinned explicitly because boto3 and botocore must come
# from the same minor series; over-constraining one without the other
# would break installation.
# -----------------------------------------------------------------------------
boto3>=1.34.0,<2.0.0                                       # AAP R-8 — AWS KMS data-key generation (ENCRYPTION_PROVIDER=aws_kms)
botocore>=1.34.0,<2.0.0                                    # boto3 transitive dependency pinned for deterministic resolution
hvac>=2.1.0,<3.0.0                                         # AAP R-8 / R-25 — HashiCorp Vault Transit (ENCRYPTION_PROVIDER=vault)

# OPERATOR NOTES
# -----------------------------------------------------------------------------
# 1. Install:
#       python -m pip install -r requirements.txt
#
# 2. Reproducible builds (optional):
#       pip-compile requirements.in -o requirements.lock
#    Lockfile generation is recommended for production builds but not
#    required by this project.
#
# 3. Provider selection at runtime (AAP R-10):
#    Even when only one provider is active per deployment (e.g., a
#    US-only deployment uses Stripe; an India-only deployment uses
#    Razorpay), BOTH provider SDKs are installed so operators can flip
#    providers via the STRIPE_ENABLED / RAZORPAY_ENABLED environment
#    variables without rebuilding the container image. This realizes
#    the "concurrent dual-provider integration" requirement of AAP R-10
#    and the Stripe ↔ Razorpay fallback path of AAP Section 0.4.2.
#
# 4. Encryption-at-rest backend (AAP R-8):
#    The KMS backend is selected at runtime via the ENCRYPTION_PROVIDER
#    environment variable. boto3 is included for AWS KMS, hvac for
#    HashiCorp Vault Transit. Add cloud-specific KMS clients
#    (google-cloud-kms, azure-keyvault-keys) to a deployment-specific
#    requirements-extra.txt if needed; do NOT add them to this manifest
#    unless they become a baseline requirement.
#
# 5. Container build dependencies (Dockerfile builder stage):
#    System packages required to compile the wheels above:
#       libpq-dev          (psycopg)
#       librdkafka-dev     (confluent-kafka)
#       libssl-dev         (cryptography)
#       libffi-dev         (cryptography / cffi)
#       build-essential    (general C/C++ toolchain)
#    Runtime stage installs only the shared-library counterparts:
#       libpq5
#       librdkafka1
#       libssl3
#
# 6. Schema Registry compatibility:
#    confluent-kafka[schemaregistry] transitively pulls `requests`. Do
#    not duplicate-pin requests in this manifest.
#
# 7. psycopg v3 vs v2:
#    This manifest installs psycopg v3 (`import psycopg`). Code MUST NOT
#    use `import psycopg2`. SQLAlchemy 2.0 async wires through the
#    `postgresql+psycopg://` dialect URL — see
#    src/repository/payment_repository.py for the canonical wiring.
#
# 8. JWT validation only (AAP R-21):
#    This service holds NO signing keys. pyjwt is used solely to verify
#    RS256 / ES256 signatures against the Auth Service's public JWKS
#    keyset. Any code path that attempts to call `jwt.encode()` with an
#    asymmetric private key violates the architectural contract and
#    must be rejected in code review.
#
# 9. SECURITY NOTICE — Payment Data Handling:
#    This service handles payment data and is in PCI-DSS scope. Operators
#    and contributors MUST observe the following invariants when
#    extending this manifest:
#
#      a. NEVER add a package that logs full request/response bodies by
#         default (e.g., debugging middlewares with body capture).
#      b. NEVER add a package that persists arbitrary data outside
#         payment_db (no extra storage backends without architectural
#         review).
#      c. NEVER add a debug middleware or profiler that exposes secrets
#         in logs, response headers, or stack traces.
#      d. Stripe and Razorpay API keys, JWT signing keys, KMS key IDs,
#         and webhook signing secrets MUST come from Kubernetes Secrets
#         or a secret manager — NEVER from `.env` files in production
#         (AAP R-25).
#      e. CVE-driven version bumps to `cryptography`, `pyjwt`, `stripe`,
#         `razorpay`, `boto3`, and `hvac` MUST be expedited;
#         `pip-audit -r requirements.txt` is part of the CI pipeline.
