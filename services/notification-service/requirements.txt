# =============================================================================
# Notification Service — Python Dependencies
# =============================================================================
# Target runtime  : Python 3.11+
# Service domain  : Multi-channel transactional notification dispatcher
#                   (Email + SMS) consuming domain events from Kafka and
#                   fanning out to provider APIs.
# Source of truth : Agent Action Plan (AAP) Section 0.3.1 (public packages),
#                   Section 0.3.3 (dependency updates), Section 0.4.2
#                   (Email + SMS provider integrations + retries + DLQ),
#                   Section 0.4.4 (notification_db PostgreSQL schema), and
#                   applicable rules R-11 (dual-channel concurrent provider
#                   integration), R-14 (Schema Registry), R-15 (retry with
#                   exponential backoff + jitter), R-16 (circuit breaker),
#                   R-17 (DLQ / retry topics), R-21 / R-22 (JWT validation
#                   with bounded TTL JWKS cache), R-26 / R-27 (structured
#                   JSON logs shipped via Beats to Logstash), R-30 (event
#                   naming conventions).
#
# Pinning policy  : Every package carries a lower bound (>=) and an upper
#                   bound (<) excluding the next major version. This permits
#                   safe patch / minor upgrades while preventing breaking
#                   major-version drift. No package is left bare; no `==`
#                   pinning is used unless accompanied by a "# pin: <reason>"
#                   comment.
#
# Ordering        : Grouped by concern, alphabetized within each group for
#                   deterministic diffs. Runtime dependencies appear first;
#                   testing (dev) dependencies are gathered at the bottom
#                   under the "Testing (dev)" banner.
#
# Install         : python -m pip install -r requirements.txt
# Compile wheels  : pip wheel -r requirements.txt -w /tmp/wheels
# Audit CVEs      : pip-audit -r requirements.txt
# =============================================================================

# -----------------------------------------------------------------------------
# Kafka — Event Streaming Backbone
# -----------------------------------------------------------------------------
# confluent-kafka wraps librdkafka for high-throughput consume; the
# [avro,schemaregistry,json] extras stream events through Schema Registry

# R-30) and routes failures to `<topic>.retry` then `<topic>.dlq` per

# to share operational tooling and monitoring dashboards.
# -----------------------------------------------------------------------------

# -----------------------------------------------------------------------------
# Database — PostgreSQL (notification_db)
# -----------------------------------------------------------------------------
# The Notification Service owns its own data store per AAP Rule R-6
# (database-per-service). The store is PostgreSQL with four tables —
# `notification_log`, `delivery_attempts`, `templates`, `user_channel_prefs`
# — per AAP Section 0.4.4. psycopg v3 (NOT psycopg2) provides native asyncio
# support and a built-in connection pool; SQLAlchemy 2.0 layers async ORM
# / query-builder semantics on top. alembic runs migrations under
# `migrations/` on container startup or via a dedicated migration job.
# -----------------------------------------------------------------------------

psycopg[binary,pool]>=3.1.18,<4.0.0                        # PostgreSQL driver v3 (binary wheel + connection pool)
sqlalchemy>=2.0.25,<3.0.0                                  # AAP Section 0.4.4 — async ORM / query builder over psycopg v3


# -----------------------------------------------------------------------------
# HTTP Client — Outbound to Provider APIs
# -----------------------------------------------------------------------------
# httpx is the async-first HTTP client used by EmailChannel (SendGrid
# REST mode) and SmsChannel (Twilio REST mode). It supports per-request
# timeouts, transport-level retries (combined with `tenacity` below),
# HTTP/2, and cleanly integrates with respx for tests. Outbound calls to
# both Stripe-equivalent provider APIs are wrapped by the resilience
# decorators per AAP R-15 / R-16.
# -----------------------------------------------------------------------------
httpx>=0.27.0,<1.0.0                                       # AAP Section 0.4.2 — async HTTP client w/ HTTP/2 + timeouts


# -----------------------------------------------------------------------------
# Email Providers (AAP R-11 — dual-provider concurrent integration)
# -----------------------------------------------------------------------------
# Per AAP R-11 the EmailChannel must support multiple providers concurrently
# behind a single `NotificationChannel` interface; provider selection is
# data-driven at runtime via the EMAIL_PROVIDER environment variable. We
# install BOTH SendGrid and AWS SES SDKs so operators can flip providers
# without rebuilding the container image. boto3 conveniently serves both
# AWS SES (email) and AWS SNS (SMS) — it appears once in this manifest and
# is referenced from the SMS group below. botocore is pinned explicitly
# because boto3 and botocore must come from the same minor series; over-
# constraining one without the other would break installation.
# -----------------------------------------------------------------------------
boto3>=1.34.0,<2.0.0                                       # AAP R-11 — AWS SES (email) + AWS SNS (SMS) adapters share this SDK
botocore>=1.34.0,<2.0.0                                    # boto3 transitive dependency pinned for deterministic resolution
sendgrid>=6.11.0,<7.0.0                                    # AAP R-11 — EmailChannel adapter (official SendGrid SDK)


# -----------------------------------------------------------------------------
# SMS Providers (AAP R-11 — dual-provider concurrent integration)
# -----------------------------------------------------------------------------
# Per AAP R-11 the SmsChannel must support multiple providers concurrently
# behind the `NotificationChannel` interface; provider selection is data-
# driven at runtime via the SMS_PROVIDER environment variable. We install
# BOTH the Twilio SDK and (transitively, via boto3 above) the AWS SNS SDK.
# Twilio's sync client is wrapped with run_in_executor for async use, or

# -----------------------------------------------------------------------------
# Resilience — Retry, Backoff, Circuit Breaker
# -----------------------------------------------------------------------------
# tenacity provides retry decorators with exponential backoff + jitter,
# bounded attempts, and configurable predicates per AAP R-15. pybreaker
# wraps each outbound provider call site with a thread-safe in-process
# circuit breaker (open / half-open / closed) per AAP R-16. Both libraries
# are explicitly listed as canonical examples in AAP Section 0.3.1
# alongside resilience4j and opossum, and they match the resilience stack
# used by sibling `recommendation-engine` for operational consistency.
# -----------------------------------------------------------------------------
pybreaker>=1.2.0,<2.0.0                                    # AAP R-16 — circuit breaker (open / half-open / closed states)
tenacity>=8.2.3,<9.0.0                                     # AAP R-15 — retry w/ exponential backoff + jitter, bounded attempts


# -----------------------------------------------------------------------------
# Authentication — JWT Validation Only
# -----------------------------------------------------------------------------
# Per AAP R-21, the Auth Service is the SOLE issuer of JWT tokens; this
# service VALIDATES ONLY, never signs. pyjwt[crypto] supports RS256/ES256
# verification using public keys fetched from the Auth Service JWKS
# endpoint. cachetools provides the bounded-TTL JWKS key cache mandated
# by AAP R-22 — keys are refreshed automatically without restart, which
# enables seamless key rotation in the Auth Service.
# -----------------------------------------------------------------------------
cachetools>=5.3.0,<6.0.0                                   # AAP R-22 — bounded TTL cache for JWKS keys
pyjwt[crypto]>=2.8.0,<3.0.0                                # AAP R-21 / R-22 — JWT validation only (RS256/ES256)

# =============================================================================
# OPERATOR NOTES
# -----------------------------------------------------------------------------
# 1. Install:
#       python -m pip install -r requirements.txt
#
# 2. Reproducible builds (optional):
#       pip-compile requirements.in -o requirements.lock
#    Lockfile generation is recommended for production builds but not
#    required by this project.
#
# 3. Provider selection at runtime (AAP R-11):
#    Even when only one provider is active per deployment, BOTH SendGrid
#    and AWS SES SDKs are installed for email, and BOTH Twilio and AWS
#    SNS SDKs are installed for SMS, so operators can flip providers via
#    the EMAIL_PROVIDER and SMS_PROVIDER environment variables without
#    rebuilding the container image. This realizes the "concurrent dual-
#    provider integration" requirement of AAP R-11.
#
# 4. Container build dependencies (Dockerfile builder stage):
#    System packages required to compile the wheels above:
#       libpq-dev          (psycopg)
#       librdkafka-dev     (confluent-kafka)
#       libssl-dev         (cryptography)
#       libffi-dev         (cryptography / cffi)
#       build-essential    (general C/C++ toolchain)
#    Runtime stage installs only the shared-library counterparts:
#       libpq5
#       librdkafka1
#       libssl3
#
# 5. Schema Registry compatibility:
#    confluent-kafka[schemaregistry] transitively pulls `requests`. Do not
#    duplicate-pin requests in this manifest.
#
# 6. psycopg v3 vs v2:
#    This manifest installs psycopg v3 (`import psycopg`). Code MUST NOT
#    use `import psycopg2`. SQLAlchemy 2.0 async wires through the
#    `postgresql+psycopg://` dialect URL — see
#    src/repository/notification_repository.py for the canonical wiring.
#
# 7. JWT validation only (AAP R-21):
#    This service holds NO signing keys. pyjwt is used solely to verify
#    RS256/ES256 signatures against the Auth Service's public JWKS keyset.
#    Any code path that attempts to call jwt.encode() with an asymmetric
#    private key violates the architectural contract and must be rejected
#    in code review.
